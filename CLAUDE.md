# Fast File Recovery: project guide

**Fast File Recovery** (short name **FFR**) is a desktop app, **Made by Akulav**, that recovers deleted and lost files from a disk. It is written **only in Rust**. There is no web view, no JavaScript and no bundler. It ships for three platforms:

| OS | Target | Release file (the only file for that OS) |
|---|---|---|
| Windows 10/11 x64 | `x86_64-pc-windows-msvc` | `FastFileRecovery-setup.exe` |
| Linux x64 | `x86_64-unknown-linux-gnu` (built with `cargo zigbuild` for glibc 2.28+) | `fast-file-recovery-linux-x64` |
| macOS Apple Silicon | `aarch64-apple-darwin` | `fast-file-recovery-macos-arm64` |

The same file does both jobs on each OS: it installs the app the first time and updates it later. There are no separate update packages, no DMG, no MSI and no zip. Each release has three binaries plus `SHA256SUMS.txt`.

This file is the architecture spec and the working rules. The release workflow, installer, updater, data location, license and README layout follow [Akulav/akulav-mc-launcher](https://github.com/Akulav/akulav-mc-launcher) on purpose. When this file is unclear, do what that project does.

## 1. Product rules (non-negotiable)

1. **Never write to the source disk.** Every handle to the source is opened read-only. All output goes to a destination on a **different physical disk**, and the app enforces this (§5.6). No override exists.
2. **Lock the source disk** for the length of a scan, so the OS cannot write to it or reuse freed clusters (§5.2).
3. **Speed is a feature.** The scan saturates the device's sequential read speed, and matching runs on every core (§5.4). The UI never blocks.
4. **Results appear live.** Found files show up while the scan runs, grouped by extension and category, and can be previewed.
5. **Look clean and beautiful.** The UI is themed, consistent and animated, with no default-egui look (§6).
6. **Branding:** "Made by Akulav" appears in the sidebar footer, the About screen, the exe and setup version info, the Linux `.desktop` comment and the macOS `Info.plist`.
7. **Icons everywhere:** the exe file, the setup file, the running process and window, the taskbar or dock, the uninstaller entry, the Linux desktop entry and the macOS bundle (§9).

## 4. Process model and elevation

Raw disk access needs admin or root. FFR uses **one process**:

- **Windows:** `ffr.manifest` sets `requestedExecutionLevel level="requireAdministrator"`, so UAC prompts once at launch. The app also declares `dpiAware`/PerMonitorV2 and `longPathAware`.
- **Linux:** if `geteuid() != 0`, the Source screen shows a "Restart with administrator rights" button. It relaunches the same binary through `pkexec env DISPLAY=… WAYLAND_DISPLAY=… XDG_RUNTIME_DIR=… XAUTHORITY=… FFR_ORIG_UID=<uid> <exe> --elevated`. Recovered files and the destination folder are `chown`ed back to `FFR_ORIG_UID` so the user owns them. Without root the app can still scan **disk image files**.
- **macOS:** the same idea via `osascript -e 'do shell script "<exe> --elevated" with administrator privileges'`. The About screen explains Full Disk Access. Internal sealed system volumes can't be read raw on Apple Silicon; the UI says so instead of failing silently. External disks and images work.

Elevated code paths must never touch the update or install logic as root on Linux or macOS. Updates always run in the user's non-elevated instance (§8).

## 5. Recovery engine (`ffr-core`)

### 5.1 Device enumeration (`device/`)

`fn list_devices() -> Vec<DeviceInfo>`, refreshed on demand and every 3 s on the Source screen (hot-plug).

```rust
struct DeviceInfo {
    id: DeviceId,                // stable per session: PhysicalDriveN | /dev/sdX | /dev/diskN
    path: PathBuf,               // raw path to open
    kind: DeviceKind,            // PhysicalDisk | Volume | ImageFile
    model: String, serial: Option<String>,
    bus: BusType,                // Nvme | Sata | Usb | Sd | Virtual | Unknown
    size: u64, sector_size: u32, // logical; physical sector size kept for alignment
    rotational: Option<bool>,    // drives the I/O strategy
    removable: bool,
    is_system: bool,             // holds the running OS → warn, cannot lock
    partitions: Vec<PartitionInfo>, // offset, len, fs type, label, mount point(s)
}
```

- **Windows:** `SetupDiGetClassDevs(GUID_DEVINTERFACE_DISK)`, then `IOCTL_STORAGE_QUERY_PROPERTY` (model, bus, `StorageDeviceSeekPenaltyProperty` → rotational), `IOCTL_DISK_GET_DRIVE_GEOMETRY_EX`, `IOCTL_DISK_GET_DRIVE_LAYOUT_EX`, and `GetLogicalDriveStrings` + `IOCTL_STORAGE_GET_DEVICE_NUMBER` to map volumes ↔ physical disks.
- **Linux:** `/sys/block/*` (size, `queue/rotational`, `queue/logical_block_size`, `removable`, `device/model`) and `/proc/self/mountinfo` for mounts. Skip `loop*` (unless the user adds one), `ram*` and `zram*`.
- **macOS:** `diskutil list -plist` + `diskutil info -plist <disk>` (parsed with `plist`), read via `/dev/rdiskN` (raw, unbuffered).
- **Image files:** `.img`, `.dd`, `.raw`, `.bin`, `.iso` and FFR's own images can be added with "Open disk image…" and are treated like a device.

### 5.2 Opening and locking the source (`device/`)

`fn open_source(dev, LockMode) -> Result<SourceHandle>`. `SourceHandle` only has `read_at(&self, offset, &mut [u8])`. **No write method exists in the type.**

| OS | Open | Lock (default: on) |
|---|---|---|
| Windows | `CreateFileW(GENERIC_READ, FILE_SHARE_READ\|FILE_SHARE_WRITE, FILE_FLAG_NO_BUFFERING)` on `\\.\PhysicalDriveN` | For every volume on that disk: open `\\.\X:`, `FSCTL_LOCK_VOLUME`, then `FSCTL_DISMOUNT_VOLUME`. Keep those handles open until the scan ends, which keeps the OS from writing. |
| Linux | `open(O_RDONLY \| O_DIRECT \| O_CLOEXEC)`; fall back without `O_DIRECT` for images | `ioctl(BLKROSET, 1)` on the disk and each partition. Unmount the partitions after the user confirms; the previous RO state is restored on exit. |
| macOS | `open("/dev/rdiskN", O_RDONLY)`, `F_NOCACHE` | `diskutil unmountDisk /dev/diskN` after the user confirms, `mountDisk` on exit if they want |

- A **system disk** can't be locked. The UI shows an amber warning ("Windows is running from this disk; new writes may overwrite deleted data. Stop using the PC and scan, or make an image from another computer.") and continues read-only and unlocked.
- If locking fails because files are open, show which volumes failed and offer: retry, continue unlocked, or cancel.
- Locks are released through `Drop` on every path, including panics (`catch_unwind` around the engine thread) and cancel.

### 5.3 Scan modes

| Mode | What it does | Gives names/paths | Speed |
|---|---|---|---|
| **Quick scan** | Reads partition tables (MBR, GPT) and filesystem metadata: NTFS `$MFT` records with the in-use flag clear (name, parent path via `$FILE_NAME`, data runs, timestamps), FAT12/16/32 deleted `0xE5` entries (+ LFN), exFAT entries with `InUse=0`. Data runs → exact extents, including fragmented NTFS files. | Yes | Seconds to minutes |
| **Deep scan** | Signature carving over the whole device (or a chosen partition or range). Works on any filesystem, including formatted, RAW, ext4, APFS, HFS+ and corrupted disks. | No (generated names) | Device read speed |
| **Full** (default) | Quick, then Deep. Deep hits whose start offset matches a Quick-scan extent are merged and not shown twice. | Both | |

ext4, btrfs, APFS and HFS+ metadata recovery is out of scope for v1 (carving covers them). The `fs::QuickScanner` trait is the extension point.

### 5.4 Deep-scan pipeline (performance core)

```
 ┌──────────── I/O stage ────────────┐   ┌──────── match stage (rayon, N = cores) ────────┐   ┌─ resolve stage ─┐
 │ reader thread(s) read_at() aligned│──▶│ Aho-Corasick over chunk (+overlap) → raw hits  │──▶│ carve::resolve  │──▶ HitsBatch
 │ chunks from BufferPool            │   │ anchored-offset check, cheap header validation │   │ size / validity │    event (≤10 Hz)
 └───────────────────────────────────┘   └────────────────────────────────────────────────┘   └─────────────────┘
          ▲ buffers recycled ◀───────────────────────────────────────────────────────────────────────┘
```

- **Chunks:** 16 MiB by default (setting: 4 to 64 MiB), aligned to the physical sector size. Each chunk is matched with an **overlap** equal to the longest `signature offset + magic length` (≤ 4 KiB) so hits across boundaries are not lost. Each hit is owned by the chunk where it starts, so there are no duplicates.
- **BufferPool:** page-aligned buffers allocated once (`2 × cores` buffers, capped at 1 GiB total and at 25 % of RAM). Bounded channels give backpressure, so memory is O(pool) no matter the disk size.
- **I/O strategy:** rotational or USB disks get **one** sequential reader. NVMe/SSD get **Q = 4** readers on interleaved chunk indices (setting: queue depth 1 to 16). Windows uses `ReadFile` with `OVERLAPPED` offsets; Unix uses `pread`.
- **Matching:** one `AhoCorasick` automaton built from every enabled signature's magic bytes. When a magic sits at a fixed offset inside the file (MP4 `ftyp` at +4, TAR `ustar` at +257, ISO `CD001` at +0x8001), the hit is shifted back. Optional `sector_aligned` signatures (most file systems start files on cluster boundaries) are only accepted at `offset % 512 == 0` when the setting "Only cluster-aligned starts" is on. It is on by default, which cuts false positives a lot.
- **Resolve:** each hit goes to its format's `SizeResolver` (§5.5) which may read more from the device (through its own read-only handle and a small LRU cache of 1 MiB blocks). Resolvers run on the rayon pool and are time- and byte-bounded.
- **Bad sectors:** if a chunk read fails, it is split in half recursively down to one sector, with N retries (default 2) and a growing delay. Unreadable sectors are zero-filled, recorded in `bad_ranges`, shown red on the sector map, and noted in the manifest of any file that overlaps them. Reading never stops because of read errors. If 1,000 bad sectors happen in a row, the UI suggests "Create an image first".
- **Throughput targets** (release build, 8-core machine): match stage ≥ 3 GB/s with all signatures on; scan time within 10 % of `dd` sequential read time on HDD, SATA SSD and NVMe. `cargo bench -p ffr-core` (criterion) guards the match stage.
- **Control:** `ScanHandle { cancel: AtomicBool, pause: (Mutex<bool>, Condvar) }`. Cancel stops within one chunk. Pause stops issuing reads.
- **Resume:** every 30 s and on pause/cancel, the scan writes a session checkpoint (`<config>/sessions/<id>.ffrscan`: device fingerprint = model + serial + size + first-MiB hash, settings, contiguous scanned-ranges list, hits, bad ranges). Resume is offered if the fingerprint matches.

### 5.5 Signatures and carving (`signatures/`, `carve/`)

```rust
struct Signature {
    id: &'static str, ext: &'static str, category: Category, // Images|Video|Audio|Documents|Archives|Other
    magic: &'static [&'static [u8]], magic_offset: u64,
    min_size: u64, max_size: u64,      // hard bounds; result clamped to max_size
    resolver: SizeResolver,
}
enum SizeResolver {
    Structured(fn(&mut Reader, start) -> Option<Carved>), // parse the format's own structure
    Footer { footer: &'static [u8], include_footer: bool, search_limit: u64 },
    HeaderSize(fn(&[u8]) -> Option<u64>),                 // size stored in header
    Fixed(u64),
    NextHeaderOrMax,                                     // last resort, confidence Low
}
struct Carved { len: u64, confidence: Confidence /* High|Medium|Low */, meta: Option<FileMeta> /* dims, duration, title… */ }
```

Formats for v1 (each has a resolver and a unit test with a real sample file under `crates/ffr-core/tests/samples/`, ≤ 50 KiB each):

| Category | Formats → resolver |
|---|---|
| Images | JPEG (marker walk SOI→EOI, handles embedded EXIF thumbnails), PNG (chunk walk to IEND, CRC check), GIF (block walk to `;`), BMP (header size), TIFF/DNG/CR2/NEF/ARW (IFD walk → max strip/tile end), WebP (RIFF size), HEIC/AVIF (ISO-BMFF box walk), PSD (section lengths), ICO |
| Video | MP4/MOV/M4V/3GP (ISO-BMFF top-level box walk, needs `moov`+`mdat`), AVI (RIFF size), MKV/WebM (EBML segment size), FLV, MPEG-TS (188-byte sync run), WMV/ASF (header object size) |
| Audio | MP3 (ID3v2 size + MPEG frame walk), WAV (RIFF), FLAC (metadata blocks + frame walk), OGG (page walk to EOS), M4A (BMFF), AAC ADTS, AIFF, MIDI |
| Documents | PDF (`%%EOF` footer, last one within limit), DOCX/XLSX/PPTX/ODT/ODS/EPUB/JAR/APK (ZIP: local headers → EOCD, sub-type chosen from `[Content_Types].xml` / `mimetype`), DOC/XLS/PPT/MSG (OLE CFB: sector count from FAT), RTF (brace balance), XML/HTML/TXT are **off by default** (noisy) |
| Archives | ZIP, RAR4/RAR5 (block walk to end marker), 7z (start header → next header end), GZIP (deflate stream end via `miniz_oxide`), BZIP2, XZ, TAR (header walk), ISO, CAB |
| Other | SQLite (page size × page count), PE EXE/DLL (section table end), ELF, Mach-O, EML, PST/OST (header size), KDBX, VMDK/VHD/VHDX, TTF/OTF/WOFF |

The signature registry is data, not scattered code. Adding a format means one entry, one resolver, one sample and one test. The Settings screen lists every format with a checkbox, grouped by category, with presets "Photos & videos", "Documents", "Everything".

### 5.6 Recovery writer (`recover/`)

- **Destination check (hard block):** canonicalize the destination path → resolve its volume → resolve the physical disk (same mapping as §5.1). If the source is a physical disk and the destination is on that same disk, recovery is refused. When the source is an image file, any destination is allowed except the image file itself. The Recover button stays disabled with the reason shown inline. Also check: free space ≥ selected total + 1 %, writable, and that the path is not a network share that is too slow (warning only).
- **Layout options:** `By type` (default: `<dest>/FFR_<date>_<time>/<Category>/<ext>/`), `Original paths` (Quick-scan hits keep their folder tree, carved ones go to `_Carved/<ext>/`), `Flat`.
- **Names:** Quick-scan hits keep the original name (made unique with ` (2)`). Carved hits are named `<ext>_<offset-hex>[_<WxH>|_<title>].<ext>`.
- **Writing:** a bounded pool (2 writers on HDD destinations, 4 otherwise) reads the extents from the source handle and writes via `BufWriter` (1 MiB). Files get original timestamps when known. Partial/bad-sector files get a `.partial` suffix if the setting asks for it, otherwise they're written with zero-fill and flagged in the manifest.
- **Manifest:** `<run folder>/ffr-report.csv` + `ffr-report.json`. Each row has: name, source offset, length, category, confidence, original path, BLAKE3, bad-sector overlap, status.
- **Disk image creation:** "Create disk image…" copies the whole source (or a range) to an `.img` file on another disk with the same bad-sector policy. It writes `<name>.img.ffrmap` (bad ranges) and shows its own progress. The image can then be scanned with no further wear on a failing drive.

### 5.7 Engine API (the only surface the GUI uses)

```rust
pub fn start_scan(source: SourceSpec, opts: ScanOptions) -> (ScanHandle, Receiver<ScanEvent>);
pub fn start_recovery(session: &Session, selection: Vec<HitId>, opts: RecoverOptions) -> (JobHandle, Receiver<RecoverEvent>);
pub fn start_imaging(source: SourceSpec, dest: PathBuf, opts: ImageOptions) -> (JobHandle, Receiver<ImageEvent>);
enum ScanEvent { Phase(Phase), Progress { bytes_done, bytes_total, bytes_per_sec, eta }, Hits(Vec<Hit>), BadRange(Range<u64>), SectorMap(Vec<u8>), Warning(String), Done(Summary), Failed(ScanError) }
```

Events are batched by the engine to at most 10 per second. The GUI drains the channel at the start of each frame and calls `ctx.request_repaint_after(100 ms)` while a job runs. Hits are kept in a `Vec<Hit>` (≈ 48 bytes each) plus per-category/extension indices, so 5 million hits stay under 300 MB.

## 7. Settings and data locations

**Everything the app writes lives in the install folder the user chose, next to the program.** Never `%APPDATA%`, `~/.config`, `~/.local/state`, the temp folder or any other system folder (`paths.rs`, `install/mod.rs`).

| File / folder in the install folder | Contents |
|---|---|
| `settings.toml` | settings (window geometry included) |
| `sessions/` | saved and resumable scans |
| `logs/` | daily logs, 7 kept |
| `update/` | a downloaded update while it is applied (removed on the next start) |
| `.ffr-install` | marker; holds the installed version |

| OS | Default install folder (user picks any) |
|---|---|
| Windows | `%LOCALAPPDATA%\Programs\FastFileRecovery\` (Inno asks once) |
| Linux | `~/.local/share/fast-file-recovery/` + `~/.local/bin/fast-file-recovery` symlink, menu entry, icons |
| macOS | `~/Applications/Fast File Recovery/` holding `Fast File Recovery.app` |

- Not installed ("Just run it", `--portable`, dev builds): data goes next to the program. `FFR_DATA_DIR` overrides.
- Only outside the folder: shortcuts/menu entries/icons, and on Linux/macOS a one-line pointer to the install folder (`<old config dir>/install-dir`; Windows uses Inno's own registry entry).
- Data from versions before 0.1.3 (`%APPDATA%\FastFileRecovery`, `~/.config/fast-file-recovery` + `~/.local/state/fast-file-recovery`, `~/Library/Application Support/FastFileRecovery`) is moved into the install folder on the first start of the installed copy, across drives too.
- The elevated copy on Linux/macOS runs from the same folder and hands files it writes back to `FFR_ORIG_UID`; it never installs, updates or moves data. Updates never touch settings, sessions or logs. Settings have a `version` field and migrate forward.

## 8. Install, update and uninstall (one binary per OS)

### 8.1 Windows: Inno Setup (`installer/ffr.iss`)

- `FastFileRecovery-setup.exe` holds the app exe. It is the first-install wizard **and** the update package.
- `AppId={{<GUID generated once>}` **never changes.** `PrivilegesRequired=lowest`, `DefaultDirName={localappdata}\Programs\FastFileRecovery`, `DisableDirPage=auto` + `UsePreviousAppDir=yes` (asks for the folder once, with a note that all data goes there), writes `{app}\.ffr-install` after install, `DisableProgramGroupPage=yes`, `SetupIconFile=..\assets\icons\icon.ico`, `UninstallDisplayIcon={app}\fast-file-recovery.exe`, `WizardStyle=modern`, `WizardImageFile`/`WizardSmallImageFile` from `installer/`, `AppPublisher=Akulav`, `AppVersion` from `/DAppVersion=` on the `iscc` command line, `VersionInfoVersion`, `VersionInfoCompany=Akulav`, `VersionInfoDescription=Fast File Recovery Setup`, `CloseApplications=force`, `ArchitecturesAllowed=x64compatible`. Languages: English and Romanian.
- Shortcuts: Start menu (always), desktop (optional task, checked by default).
- **Update mode:** the app runs `FastFileRecovery-setup.exe /VERYSILENT /SUPPRESSMSGBOXES /NORESTART /CLOSEAPPLICATIONS /UPDATE` and exits. A `[Code]` function `IsUpdate()` checks for `/UPDATE`, and the `[Run]` entry `Filename: {app}\fast-file-recovery.exe; Flags: nowait runasoriginaluser; Check: IsUpdate` relaunches the app after a silent update. The interactive install ends with a normal "Launch Fast File Recovery" `postinstall` checkbox.
- Installing over an existing install upgrades it in place (same AppId). No old-uninstaller dance is needed in v1.
- **Update mode** passes `/DIR=<current install folder>` so the update always lands in the same folder.
- **Uninstall:** removes the program and shortcuts, then asks "Also delete settings, saved scans and logs?" (default No) and deletes only the app's own entries in `{app}` (plus the pre-0.1.3 `%APPDATA%\FastFileRecovery`). It never deletes data when silent.
- `.iss` files are **UTF-8 with BOM.**

### 8.2 Linux: self-installing binary

`fast-file-recovery-linux-x64`, on start:
- If it runs from outside the install folder and no install exists → show a small **install dialog** in the egui window with an **install folder** field (default `~/.local/share/fast-file-recovery`) and "Install" / "Just run it". Install = copy itself to `<folder>/fast-file-recovery`, write `.ffr-install`, remember the folder, `chmod 755`, symlink `~/.local/bin/fast-file-recovery`, write `~/.local/share/applications/fast-file-recovery.desktop` (`Comment=Recover deleted files — Made by Akulav`, `Icon=fast-file-recovery`, `StartupWMClass=fast-file-recovery`), write icons from embedded PNGs into `~/.local/share/icons/hicolor/<size>/apps/`, run `update-desktop-database`/`gtk-update-icon-cache` if present (ignore failures), then relaunch from the install location.
- If an install exists and this binary is newer → offer "Update installed copy" (into its folder).
- Flags: `--version`, `--here` (run without installing or prompting), `--portable`, `--uninstall [--delete-data]`.

### 8.3 macOS: self-installing binary

`fast-file-recovery-macos-arm64` (ad-hoc signed with `codesign -s -` in CI), on start:
- If it isn't running from an installed `Fast File Recovery.app` → offer install into a folder the user picks (default `~/Applications/Fast File Recovery`): create `<folder>/Fast File Recovery.app/Contents/{MacOS,Resources}`, write `<folder>/.ffr-install`, copy itself to `Contents/MacOS/fast-file-recovery`, write the embedded `icon.icns` and an `Info.plist` (`CFBundleIdentifier=com.akulav.fastfilerecovery`, `CFBundleIconFile=icon`, `CFBundleShortVersionString`, `NSHumanReadableCopyright=Made by Akulav`, `LSMinimumSystemVersion=12.0`, `NSHighResolutionCapable=true`), ad-hoc sign the bundle (`codesign --force --deep -s -`), then `open` it.
- Same `--version`, `--here`, `--uninstall [--delete-data]` flags.
- The README explains the first-open steps for a quarantined download: right-click → Open, or `xattr -d com.apple.quarantine <file>`.

### 8.4 Updater (`updater.rs`)

- **Source:** `https://api.github.com/repos/Akulav/fast-file-recovery/releases/latest` (pre-releases only if the current version is a pre-release). The User-Agent is `fast-file-recovery/<version>`.
- **When:** 20 s after start and every 6 h if "Check automatically" is on (default on), plus the **Check for updates** button. A check never blocks the UI (background thread + channel). Results: up to date / update available (version + notes) / error (shown, retry offered).
- **Update button:** download the asset for this OS (exact names from the table at the top) into a fresh folder under `<install folder>/update/` (never the temp folder) with a progress bar → download `SHA256SUMS.txt` → **verify SHA-256** (mismatch → delete, error, stop) → apply:
  - Windows: run the setup in update mode (§8.1), exit the app.
  - Linux: write `<install>.new`, `chmod 755`, rename the current binary to `.old`, rename `.new` into place (atomic on the same fs), relaunch, exit. The next start deletes `.old`.
  - macOS: same swap inside `Contents/MacOS/`, re-sign the bundle ad-hoc, relaunch via `open -n`, exit.
- **Never during a scan or recovery.** The Update button is disabled with "Finish or stop the current job first."
- **Local builds never update themselves.** Only CI release builds set `FFR_RELEASE_BUILD=1`, read with `option_env!`. Local builds show "Development build: updates disabled" in About.
- Nothing installs without the user clicking Update.
- Release asset names and `SHA256SUMS.txt` are **API**: installed copies look for them. Never rename them.

## 10. Versioning, changelog and commits

- **Source of truth:** `[workspace.package] version` in the root `Cargo.toml`. Crates use `version.workspace = true`. Current: **0.1.0** (first release once the app exists).
- **Every change ships as a release.** For each change:
  1. Add bullet(s) under `## [Unreleased]` in `CHANGELOG.md` (Keep a Changelog sections: Added / Changed / Fixed / Removed), written for users.
  2. `cargo xtask bump patch|minor|major`: `patch` for fixes and cleanup, `minor` for user-visible additions, `major` only when the user asks. It updates `Cargo.toml`, refreshes `Cargo.lock` (`cargo update -w`) and turns `[Unreleased]` into `## [X.Y.Z] - YYYY-MM-DD` with a fresh empty `[Unreleased]` above it.
  3. Run the checks (§12) and report results honestly.
  4. **Commit automatically** as `Release vX.Y.Z: <short summary>`, with the changelog section as the commit body. Commit everything for that change in one commit (including lockfile changes).
- **Pushing is the user's call** (they push from GitHub Desktop). Never push, and never create or push tags by hand. CI creates the tag.
- `cargo xtask release [--no-push]`: pre-push checks (versions agree, changelog section exists and isn't empty, clean tree, tag `vX.Y.Z` not on the remote), then `git push`. `--no-push` only checks.
- A version with a hyphen (`0.2.0-beta.1`) becomes a GitHub pre-release.

## 11. CI and release workflows

One workflow, `.github/workflows/build.yml` (**Build & Release**), the same logic as akulav-mc-launcher. It runs on every push to `main`, every tag, every pull request and `workflow_dispatch`; `permissions: contents: write`; `FFR_RELEASE_BUILD=1` for every job. Use only maintained actions (`actions/checkout@v4`, `dtolnay/rust-toolchain`, `Swatinem/rust-cache@v2`, `softprops/action-gh-release@v2`).

1. **meta (Version):** read the version from `[workspace.package]`, check it matches every crate in `Cargo.lock`. `release=true` when the push is a tag matching the version, or a push to `main` and no GitHub release `vX.Y.Z` exists yet (nothing is published twice). Then the `CHANGELOG.md` section must exist. A hyphen → `prerelease=true`.
2. **lint:** `cargo fmt --all --check` + `cargo clippy --workspace --all-targets --locked -- -D warnings`.
3. **windows / linux / macos** (each tests, then builds its one file):
   - Windows: `cargo test` → `cargo build --release --locked -p ffr-app` → Inno Setup (`choco install innosetup` when missing) → `FastFileRecovery-setup.exe`.
   - Linux: GUI dev packages for tests, `cargo test` + the ignored round-trip test → `cargo zigbuild --release -p ffr-app --target x86_64-unknown-linux-gnu.2.28` (glibc 2.28+) → `fast-file-recovery-linux-x64`.
   - macOS 15 (arm64): `cargo test` → build `aarch64-apple-darwin` → `codesign --force -s -` → `fast-file-recovery-macos-arm64`.
4. **release** (needs all of the above, only when `release=true`): `SHA256SUMS.txt`, notes = that version's changelog section + a download table + checksums → tag `vX.Y.Z` on the built commit → GitHub release (title `Fast File Recovery vX.Y.Z`, 3 binaries + `SHA256SUMS.txt`, pre-release flag, latest when stable).

Release profile: `opt-level = 3`, `lto = "fat"`, `codegen-units = 1`, `panic = "abort"` is **not** used (the engine relies on `catch_unwind` to release disk locks), `strip = true`. Windows uses `windows_subsystem = "windows"` in release (no console). `--version` still prints via `AttachConsole(ATTACH_PARENT_PROCESS)`.

## 13. Testing strategy

- **Unit tests** per resolver, using real small sample files (`tests/samples/`, ≤ 50 KiB each, freely licensed or generated).
- **Synthetic disk round-trip** (ignored by default, slow): build a 512 MiB image filled with random noise, place every sample at random cluster-aligned and unaligned offsets (some fragmented, some crossing chunk boundaries, some truncated), run a deep scan, and assert every whole sample is found with the exact length and BLAKE3, truncated ones are flagged, and there are no duplicates.
- **Filesystem fixtures:** FAT32 and exFAT images generated in tests (`fatfs` crate: write files, delete them, scan). Small NTFS images (created once on Windows, zstd-compressed, ≤ 2 MiB) under `tests/fixtures/`.
- **Bad-sector simulation:** a `FaultyReader` test double that returns errors for configured ranges.
- **Safety tests:** the type system has no write path on `SourceHandle` (a compile-fail test via `trybuild`). The destination check refuses the source disk (unit-tested with mocked volume↔disk mapping).
- **Benchmarks:** `criterion` bench of the match stage over 256 MiB of random data with all signatures enabled.

## 17. Coding rules

- `ffr-core` has no GUI, network or install code. `ffr-app` has no raw-disk code outside calls into `ffr-core`.
- Platform code lives in `windows.rs` / `linux.rs` / `macos.rs` behind `#[cfg(target_os = …)]` with one shared trait. Never scatter `cfg` through the logic.
- `unsafe` only in the platform modules, each block with a `// SAFETY:` comment.
- No `unwrap()`/`expect()` on I/O, parsing or device data. Resolvers treat all disk bytes as hostile: bounds-checked, with size and time limits.
- The UI thread never does I/O beyond reading settings at start. Everything slow runs on a worker and reports through a channel.
- User-facing text is plain, short and friendly; error messages say what to do next.
